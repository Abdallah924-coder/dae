# DAE Crypto

Plateforme d’achat et de vente de cryptomonnaies avec API Express, MongoDB et interface React.

## Développement

Utilisez Node.js 20 ou plus récent, puis installez les dépendances avec `npm ci`.

- `npm run dev:local` démarre l’API Express sur le port 3000 avec redémarrage automatique, en lisant exclusivement `.env.local`.
- `npm run dev:client` démarre Vite sur le port 5173. La configuration Vite relaie `/api` et `/images` vers Express.
- `npm run build` compile l’interface React dans `public/app`.
- `npm start` démarre l’API. Compilez d’abord l’interface si le dossier `public/app` n’existe pas.

Pour démarrer localement sans toucher à la configuration de production, copiez `.env.local.example` en `.env.local`, puis remplacez le mot de passe et la `ADMIN_SESSION_SECRET` par des valeurs locales uniques. Ce fichier configure uniquement MongoDB sur `127.0.0.1` et laisse dépôts/retraits désactivés. Ne copiez pas le `.env` de production. `npm run dev:local` refuse de démarrer si `.env.local` n’existe pas et n’importe pas les variables de `.env`.

Si MongoDB n’est pas déjà installé et démarré localement, lancez dans un terminal `mkdir -p .local-mongo && mongod --dbpath .local-mongo --port 27018 --replSet rs0 --bind_ip 127.0.0.1`, puis initialisez le replica set une seule fois dans un autre terminal avec `mongosh --port 27018 --eval "rs.initiate()"`. Ensuite, copiez `.env.local.example` en `.env.local`, lancez `npm ci`, `npm run dev:local`, puis dans un deuxième terminal `npm run dev:client`; ouvrez `http://localhost:5173`. Arrêtez les serveurs avec `Ctrl+C`. Sur Windows PowerShell, utilisez `New-Item -ItemType Directory -Force .local-mongo`, `Copy-Item .env.local.example .env.local`, démarrez MongoDB avec les mêmes options `mongod --dbpath .local-mongo --port 27018 --replSet rs0 --bind_ip 127.0.0.1`, puis faites `mongosh --port 27018 --eval "rs.initiate()"` une seule fois.

L’API a besoin d’une base MongoDB locale compatible avec les transactions multi-documents. Les codes d’authentification sont envoyés uniquement par e-mail. Les notifications e-mail/SMS de commande et l’accès administrateur utilisent les variables documentées dans `.env.example`; ces intégrations ne sont pas nécessaires pour afficher l’interface localement.

## Déploiement Render

Render installe les dépendances, compile React avec `npm run build`, puis démarre Express. Le serveur sert les routes publiques `/`, `/acheter`, `/vendre`, `/envoyer`, `/suivi`, `/attente`, `/contact` et `/admin`, ainsi que les routes de compte `/inscription`, `/connexion`, `/mot-de-passe-oublie`, `/compte`, `/profil`, `/portefeuille`, `/transactions`, `/depot`, `/retrait`, `/staking`, `/verification` et `/securite` depuis l’application React. Les endpoints métier restent sous `/api`.

Le taux par défaut est de **635 FCFA/USDT quand le client achète** et **580 FCFA/USDT quand il vend**. Au démarrage, si le dernier taux USDT enregistré vaut encore 570 FCFA à la vente, l’application ajoute un nouveau taux à 580 en conservant l’ancien dans l’historique. Les autres taux enregistrés restent prioritaires et modifiables dans Administration → Taux & limites. Le parcours achat/vente obtient sa cotation par l’API DAE, qui calcule les montants en unités entières (8 décimales crypto, prix source à 12 décimales), arrondit le FCFA au franc selon le sens, puis signe une cotation valable cinq minutes. La commande conserve cette cotation et stocke les quantités crypto en Decimal128; une précision d’entrée supérieure à 8 décimales est refusée.

La création des commandes, leurs changements de statut et leurs événements d’audit sont validés ensemble dans une transaction MongoDB. Utilisez un replica set ou une topologie MongoDB compatible avec les transactions multi-documents. Le script `npm run expire` traite en une fois les commandes échues; planifiez son exécution régulière dans l’environnement de déploiement.

La création d’ordre est idempotente par compte : une reprise réseau avec la même clé UUID et les mêmes détails retourne la commande existante, même si la cotation a expiré; une réutilisation de la clé avec des détails différents renvoie vers la commande déjà enregistrée. Après un rechargement de page, l’interface recherche cette commande avant de proposer un nouvel envoi.

Le tableau de marché affiche 14 cryptos de référence; les liens d’achat et de vente ne sont actifs que pour les cinq actifs déjà pris en charge par le parcours d’ordre. Le graphique utilise l’API CoinGecko sur une journée et regroupe les observations récentes par heure. Il s’agit d’un repère indicatif, pas d’un carnet d’ordres DAE ni du taux contractuel FCFA de l’écran d’achat/vente. La granularité automatique et l’endpoint `market_chart` sont décrits dans la [documentation CoinGecko](https://docs.coingecko.com/reference/coins-id-market-chart). Les données horaires historiques CoinPaprika utilisées auparavant nécessitent une offre payante au-delà de la période gratuite, comme l’illustre la [documentation CoinPaprika](https://docs.coinpaprika.com/api-reference/tickers/get-historical-ticks-for-a-specific-coin).

Binance Pay est proposé comme transfert manuel, sans connexion à l’API Binance. Configurez le Binance UID de DAE dans Administration → Configuration. À l’achat, le client peut donner son UID pour recevoir les cryptos ; à la vente, il envoie les cryptos vers l’UID DAE affiché. Le paiement ou le versement en FCFA reste effectué par Mobile Money.

Les achats d’USDT sont affectés au solde interne USDT BEP20 du client : le versement n’est inscrit au grand livre que lorsque l’administration passe une commande dont le paiement a été effectivement vérifié au statut « Terminée ». La capture ou la déclaration de paiement du client ne crédite jamais le solde à elle seule. Les autres achats conservent le transfert vers le portefeuille externe choisi. La page `/transactions` rassemble l’historique des dépôts, retraits, achats et ventes. `/envoyer` ouvre le parcours de vente d’USDT BEP20 : le client transmet les USDT à l’adresse DAE affichée, donne le numéro Mobile Money du bénéficiaire et fournit la preuve; l’équipe vérifie la réception avant le paiement en FCFA. L’adresse de réception est conservée avec la commande pour rester visible dans son suivi.

## Comptes clients et conservation

Les routes `/inscription`, `/connexion`, `/mot-de-passe-oublie`, `/compte`, `/profil`, `/portefeuille`, `/transactions`, `/depot`, `/retrait`, `/staking`, `/verification` et `/securite` forment l’espace client. Les codes d’activation, de connexion et de récupération sont envoyés uniquement par e-mail; le numéro de téléphone reste une coordonnée de compte et n’est pas utilisé pour les codes d’authentification. La page Profil affiche les coordonnées du compte, l’identifiant et les liens vers les contrôles; les coordonnées ne sont pas modifiables directement depuis l’interface. La page Transactions réunit les opérations issues des registres de dépôt/retrait et des commandes d’achat/vente, avec pagination et suivi des commandes. La page Sécurité liste les sessions actives et permet de révoquer les autres appareils. La watchlist des marchés se synchronise avec le compte. Pour ouvrir l’inscription, configurez l’envoi e-mail, `CUSTOMER_AUTH_SECRET` (au moins 32 caractères aléatoires), `CUSTOMER_LEGAL_REVIEWED=true` et `PUBLIC_APP_URL=https://dae-1lpj.onrender.com`. Les variables `CUSTOMER_TERMS_VERSION`, `CUSTOMER_PRIVACY_VERSION`, `CUSTOMER_TERMS_URL` et `CUSTOMER_PRIVACY_URL` sont facultatives; le formulaire peut afficher les liens lorsqu’ils seront publiés. Cette validation d’environnement est une attestation opérateur, pas un avis juridique. Les suspensions/réactivations admin et la récupération du mot de passe révoquent les sessions dans la même transaction que le changement d’état; configurez MongoDB en replica set, cluster shardé ou topologie Load Balanced compatible. La préparation affiche si cette capacité est détectée. Les actions admin et motifs sont conservés dans un journal append-only. Les statuts KYC sont modifiables par revue manuelle depuis l’administration.

## DAE Earn

La page `/staking` présente le catalogue DAE Flexible, Bronze, Silver et Gold. Les APY sont des taux indicatifs configurables, distincts de la répartition des revenus DeFi. L’administration configure produits, limites, pénalités et les interrupteurs souscriptions/allocations/récompenses; toute modification est proposée par une identité, approuvée par la seconde et journalisée. Routes principales : `GET /api/earn/catalog`, `GET/POST /api/earn/positions`, `POST /api/earn/positions/:id/withdrawal`, `GET /api/admin/earn/actions`, `POST /api/admin/earn/actions` et `/api/admin/earn/actions/:id/approve|reject`.

Quand les souscriptions sont activées, un client actif, vérifié et KYC approuvé peut cliquer « Souscrire et verrouiller ». Dans une transaction MongoDB, le ledger transfère alors son USDT du compartiment disponible vers staké et crée une position en attente. L’activation exige le dépôt effectivement exécuté par DAE depuis sa trésorerie, un reçu BSC confirmé conforme au montant et au protocole, puis l’approbation du second administrateur. Les clés privées ne transitent pas par ce service : DAE exécute les transactions Venus/Aave hors plateforme et configure uniquement l’adresse publique `DAE_EARN_TREASURY_ADDRESS`.

La trésorerie est initialisée depuis un snapshot BSC approuvé à deux personnes. Les apports ultérieurs, dépôts protocolaires et retraits sont rapprochés avec les événements BEP-20 confirmés et des écritures idempotentes du ledger. Les reçus Venus/Aave exigent aussi les événements de dépôt/retrait du protocole, pas seulement un transfert USDT. Pour classifier une récupération, le système impute d’abord les USDT reçus au principal restant; seul le surplus est reconnu comme rendement réalisé. Ce rendement est réparti selon la configuration (70 % récompenses, 20 % revenus DAE, 10 % réserve par défaut). L’admin voit les soldes comptables et le solde USDT on-chain de la trésorerie; un écart est signalé, et les approbations recontrôlent le rapprochement.

Les récompenses quotidiennes sont calculées sur une convention simple APY/365, puis payées depuis le compte `system:earn:reward-pool`, jamais au-delà des fonds réellement alloués à ce pool. Le job est relancé par le serveur toutes les 15 minutes pour traiter la journée UTC complète, rattraper les jours manquants et retenter les demandes encore non financées. Une clé de date et des transactions de ledger idempotentes protègent contre les doubles paiements. Le bouton de retrait client crée une demande; après récupération DeFi, DAE transfère le principal de la trésorerie Earn vers `BSC_MASTER_ADDRESS`, adresse du wallet opérationnel qui doit être distincte, puis fournit le reçu confirmé pour approbation par le second admin. Le ledger reclassifie alors le cash Earn vers la réserve opérationnelle et libère le solde client dans la même transaction MongoDB. Les récompenses futures sont abandonnées après retrait anticipé; une pénalité sur récompenses déjà créditées est figée dans les conditions acceptées lors de la souscription, exige un solde disponible et ne touche jamais au principal.

Les interrupteurs financiers sont fermés par défaut et la base doit supporter les transactions MongoDB multi-documents. La double approbation, les contrôles de reçus et la réconciliation logicielle ne remplacent pas une validation juridique, une revue de sécurité indépendante, un contrôle des risques/contreparties, un test de reprise, une vérification opérationnelle des contrats et de la liquidité, ni la validation de la trésorerie réelle par DAE. Ne promettez pas de rendement et n’ouvrez pas le service aux clients avant ces validations.

La création d’un ordre d’achat ou de vente exige un compte actif avec e-mail et téléphone vérifiés; l’ouverture de session est protégée par un code envoyé sur chacun des deux canaux. Le mode invité ne peut pas créer d’ordre.

DAE opère en République du Congo et conserve les actifs de ses clients. Pour BSC, l’application dérive les adresses de dépôt depuis le xpub, indexe le jeton Binance-Peg BSC-USD, crédite le grand livre après confirmations et approbation KYC, réserve les soldes avant retrait et transmet les transactions au signataire. Les workers doivent fonctionner sur un hôte sécurisé et toujours allumé, distinct du poste de travail, et utiliser exactement le même `MONGODB_URI` de production que le site Render. Le worker des dépôts utilise `BSC_LOGS_RPC_URL` pour lire les événements de transfert (par défaut `https://bsc-rpc.publicnode.com`) et `BSC_RPC_URL` pour les autres contrôles réseau. Configurez un fournisseur RPC de confiance et vérifiez ses limites et sa disponibilité avant une exploitation réelle : l’endpoint de journaux reçoit les adresses publiques recherchées par l’indexeur. Le signataire dérive les clés clientes, maître et gaz depuis `BSC_SIGNER_MNEMONIC`, conservée dans `.env.signer` sur le VPS. Ne mettez jamais cette phrase dans Git, Render, l’API ou MongoDB. Le journal de reprise peut conserver une transaction signée chiffrée dans MongoDB, avec une clé dérivée de cette phrase. Cette architecture n’est pas un HSM/MPC ni un audit indépendant.

Les workers exécutés normalement lisent `.env`; le signataire lit aussi `.env.signer` pour la phrase secrète. Ces deux fichiers sont ignorés par Git. Pour un test local isolé, `npm run bsc:deposits:local` charge exclusivement `.env.local`; sa base de développement `mongodb://127.0.0.1:27018/usdt_cfa?replicaSet=rs0` est séparée de la production. N’activez jamais l’indexeur local avec la base de production pour tester : il écrit le curseur et le heartbeat et peut créditer de vrais dépôts.

### Workers BSC sur un VPS Linux avec systemd

Les services [`dae-bsc-deposits.service`](deploy/systemd/dae-bsc-deposits.service) et [`dae-bsc-signer.service`](deploy/systemd/dae-bsc-signer.service) maintiennent les workers actifs après fermeture de session et les redémarrent après un arrêt inattendu. Ils supposent un compte système `dae`, le dépôt installé dans `/opt/dae` et Node.js installé dans `/usr/bin/node`; adaptez `User`, `Group`, `WorkingDirectory` et `ExecStart` aux chemins du VPS si nécessaire.

1. Installez une version supportée de Node.js (20 ou ultérieure), Git et systemd sur un VPS durci. Créez un compte système sans connexion interactive, clonez le dépôt dans `/opt/dae`, installez les dépendances de production avec `npm ci --omit=dev`, puis donnez au compte `dae` un accès en lecture au code et à `node_modules`.
2. Créez `/opt/dae/.env` lisible uniquement par `dae` (`chmod 600`). Il doit contenir au minimum le même `MONGODB_URI` que Render, ainsi que les valeurs BSC vérifiées : `BSC_RPC_URL`, `BSC_LOGS_RPC_URL`, `BSC_CHAIN_ID=56`, `BSC_USDT_CONTRACT`, `BSC_HD_XPUB`, `BSC_MASTER_ADDRESS`, `BSC_GAS_ADDRESS`, `BSC_CONFIRMATIONS`, `BSC_SCAN_INTERVAL_MS`, `BSC_START_BLOCK`, `BSC_DEPOSITS_ENABLED=true` et `BSC_WITHDRAWALS_ENABLED=true`. Le VPS et Render doivent pointer vers la même base MongoDB de production; ne placez pas une URI locale ni une base différente sur le VPS.
3. Créez `/opt/dae/.env.signer` avec uniquement `BSC_SIGNER_MNEMONIC`, mode `600`, propriétaire `dae`. La phrase doit être créée et sauvegardée selon la procédure de garde de clés de DAE; ne la copiez pas depuis Git, Render, une conversation ou une machine de développement. Restreignez l’accès SSH au VPS, activez les mises à jour de sécurité et les sauvegardes chiffrées hors ligne.
4. Copiez les deux unités dans `/etc/systemd/system/`, vérifiez le chemin de Node dans chacune, puis exécutez `sudo systemctl daemon-reload`, `sudo systemctl enable --now dae-bsc-deposits dae-bsc-signer`. Vérifiez l’état avec `sudo systemctl status dae-bsc-deposits dae-bsc-signer` et les journaux avec `sudo journalctl -u dae-bsc-deposits -u dae-bsc-signer -f`.
5. Arrêtez les anciennes instances lancées depuis le poste de travail avant de démarrer ces unités : un seul indexeur et un seul signataire doivent traiter la production. Dans Render, n’activez les dépôts/retraits qu’après validation des heartbeats, de la base transactionnelle, du bloc de départ, des adresses maître/gaz et du financement BNB du portefeuille gaz. Les retraits déplacent des fonds réels; ne les activez pas comme simple test.

Si l’adresse de dépôt disparaît, vérifiez l’état du worker et son heartbeat : l’application masque volontairement l’adresse quand l’indexeur n’est plus actif. Les soldes et historiques crédités résident dans MongoDB et ne doivent pas revenir à zéro à l’arrêt du worker. Si le solde affiché vaut zéro alors que l’historique existe, vérifiez que `MONGODB_URI` sur Render et le VPS désigne exactement la même base. Staking reste désactivé. `DAE_REGULATORY_REVIEWED` est une attestation de configuration, pas une autorisation vérifiée par l’application. Voir [docs/CUSTODY_ARCHITECTURE.md](docs/CUSTODY_ARCHITECTURE.md) pour les contrôles opérationnels.
